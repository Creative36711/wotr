# Архитектура — War of the Ring Remaster

Документ для того, кто собирается менять код: карта модулей, потоки данных,
инварианты и места, которые легко сломать. Обзор проекта «сверху» — в
[README.md](../README.md).

## 1. Слои и границы

```text
┌──────────────────────────────────────────────────────────────────────┐
│ React (src/components)                                               │
│   отрисовка, инспекторы, редактор мира, модалка конфликта            │
└───────────────┬──────────────────────────────────────────────────────┘
                │ вызовы действий, подписки через селекторы
┌───────────────▼──────────────────────────────────────────────────────┐
│ Zustand-стор (src/store/useMapStore.ts)                              │
│   единственное место, где меняется состояние кампании                │
└───────┬───────────────────────────────────────────┬──────────────────┘
        │ чистые функции                            │ invoke()
┌───────▼─────────────────────┐      ┌──────────────▼──────────────────┐
│ src/game/* — игровая логика │      │ Rust (src-tauri/src)            │
│ без React, без побочных     │      │ файлы мода, ресурсы, диагностика│
│ эффектов, легко тестируется │      │ мост в BFME, распознавание      │
└─────────────────────────────┘      └──────────────┬──────────────────┘
                                                    │ Win32, BIG, PNG
                                     ┌──────────────▼──────────────────┐
                                     │ BFME2:RotWK (внешняя игра)      │
                                     └─────────────────────────────────┘
```

Правила, которые держат эту границу:

- **`src/game/*` не знает про React и не знает про Rust.** Функции принимают данные и возвращают данные. Именно поэтому их удаётся прогнать в jsdom-харнессе.
- **Весь `invoke()` спрятан в `src/dataService.ts`.** Компоненты и стор не вызывают Tauri напрямую и не проверяют `isTauriRuntime()` — это делает сервис, поэтому приложение работает и в браузере (без RTS).
- **Стор — единственный владелец состояния.** `src/game/*` мутирует только то, что ему передали (обычно клон), и возвращает результат.

## 2. Карта модулей

### Игровая логика (`src/game/`)

| Файл | Ответственность |
| --- | --- |
| `conflicts.ts` | `scanHotSpots` (где сошлись армии), `previewConflict` (предпросмотр сил и модификаторов), `calculateConflictBattle` (расчёт исхода), `updateConflictRtsCompatibility` |

| `supply.ts` | Снабжение: пул припасов армии, деградация по гексам и ходам, пополнение на транзите, бонусы атакующему, вес для автобоя |
| `ai.ts` | `runAiPlanning` / `runAiMovement` / `planAlliedMovement`, выбор цели марша с учётом сложности и снабжения |

| `heroes.ts`, `recruitment.ts`, `progression.ts`, `unitLevelCaps.ts` | Герои и их состояния, вербовка, уровни и апгрейды, лимиты уровней по объектам BFME |
| `campaign.ts`, `regions.ts`, `buildings.ts`, `economicTypes.ts`, `ring.ts`, `handicap.ts` | Фазы и стороны, контроль регионов, постройки, экономические типы, ковка Кольца, относительный гандикап для BFME |
| `fogOfWar.ts` | Видимые гексы и «последние сведения» об армиях и гарнизонах |
| `saveGame.ts` | Создание/применение/извлечение сохранения |
| `sessionLog.ts` | Журнал сессии: `logEvent`, обрезка больших объектов, ключ и папка сессии |
| `defaultData.ts` | Значения по умолчанию для экономических типов и прочего |
| `../hex/hexGrid.ts` | Осевая сетка: соседи, расстояние, поиск пути, стоимость движения |
| `../hex/movementOverlay.ts` | Подсветка проходимости при выделенной армии: категории гекса (`impassable`/`slow`/`standard` по стоимости входа) и недостижимость за оставшиеся ОД (BFS через `findReachable`) |

### Стор (`src/store/useMapStore.ts`, ~2300 строк)

Единственный Zustand-стор. Около 75 действий: режим и выделение, редактор мира
(локации, гексы, регионы, фракции, юниты, герои, армии, постройки, снабжение,
палантир, Кольцо), игровой цикл (`newGame`, `advancePhase`, `moveArmy`,
`resolveConflict`, `resolveConflictRts`, `formArmy`, `transferArmyUnit`, …),
`undo` / `redo`.

Ключевые внутренние функции цикла:

| Функция | Что делает |
| --- | --- |
| `preparePlanningSide` | Начало хода стороны: доход, вербовка, пополнение снабжения, состояния героев |
| `executePlayerOrders` | Исполняет отложенные приказы по фактически пройденному пути (с учётом перехвата) |
| `scanHotSpots` → конфликты | Находит гексы, где сошлись враждебные армии |
| `calculateConflictBattle` | Разрешает бой ИИ без RTS |
| `processAftermath` | Отступления, захваты, потери, ранения, экономика, проверка победы |

`undo` / `redo` работают через снимки: каждое действие кладёт в историю
`cloneSnapshot(...)` — глубокую копию мира. Добавляя поле в состояние, его
нужно добавить и в соответствующий `clone*`, иначе откат будет терять данные.

### Редактор игровых данных (`WorldDataEditor.tsx`)

Окно «Редактор игровых данных → Мир и кампания». Вкладка = одна сущность или
одна группа правил; правило «название вкладки описывает всё её содержимое»
соблюдается намеренно:

| Вкладка | Содержимое |
| --- | --- |
| Фракции | список фракций, стартовая казна, лимит полевых армий, цвета |
| Экономические типы | типы локаций: доход, очередь, резерв, обзор, слоты построек, боевые бонусы владельца |
| Юниты / Герои / Капитаны | составы, BFME Object ID, автобаланс, условия открытия героев |
| Стартовые армии | армии, с которых начинается кампания |
| Постройки | типы построек, стоимость, апгрейды, бонусы владельцу и атакующему отсюда |
| Кольцо | **только** ковка Кольца Всевластья |
| Снабжение | **только** снабжение армий: деградация и правила пополнения |
| Регионы | регионы, цвет, состав гексов |
| Интеграция BFME | порядок фракций, BIG-файлы мода, архив карт, сетевые правила, потолок бонусов палантира |

Потолки палантира живут во вкладке интеграции, а не в «Кольце»: это ограничение
на то, что получает игра, рядом с сетевыми правилами про ресурсы и очки
командования.

## 3. Модель данных

Единый источник правды — `src/types.ts`. Важные сущности:

```text
WorldData        мир: локации, сетка, фракции, экономические типы, регионы, кампании
RosterData       юниты, герои, капитаны
MapLocation      объект карты: structuralType + economicType + hex + regionId
                 + rtsMapId / rtsMapCache / rtsPositions / rtsFortress
Army             состав (unitSlots/heroSlots), командир, статус, supplyPool
CampaignState    раунд, фаза, порядок хода, казначейства, состояния локаций и героев,
                 туман войны, конфликты, отложенные приказы, журнал
SaveGameData     сохранение: версия формата + версия приложения + снимок кампании
```

Загрузка и сохранение — `src/dataService.ts`:

- `normalizeWorld` / `normalizeRoster` / `normalizeSaveGame` приводят внешние JSON к типам и **подставляют значения по умолчанию для отсутствующих блоков**. Благодаря этому старые моды без новых полей (например, без `supplySettings`) работают без миграции.
- Проверка сохранения: `source.version === SAVEGAME_DATA_VERSION && source.gameVersion === GAME_VERSION && modId совпадает`. Иначе сохранение считается несовместимым. Миграций нет — намеренно.
- `SAVE_VERSION` в `src-tauri/src/lib.rs` должен совпадать с `SAVEGAME_DATA_VERSION`; расхождение ловит `scripts/check-version.mjs`.

### Локализация

Английский — канонический и хранится в самом поле (`name`, `label`,
`description`). Переводы лежат рядом: `nameTranslations: { ru: "…" }`.
Технические ID стабильны и никогда не являются именами. Словарь интерфейса —
`src/i18n.tsx`, переводы контента — в данных мода, поэтому новый язык
переносится вместе с модом без изменения схемы.

## 4. Поток данных: ход

```text
newGame(factionId)
  → preparePlanningSide('good')          доход, вербовка, снабжение, герои
  → (если игрок за Тьму) preparePlanningSide('evil') + ИИ за Свет

advancePhase() по фазам:
  planning_*    → executePlayerOrders() + ИИ-планирование остальных фракций
  movement_first→ executePlayerOrders()          приказы игрока по фактическому пути
                  runAiMovement('good'|'evil')   марши ИИ
  movement_second→ то же для второй половины движения
  conflicts     → scanHotSpots() → список CampaignConflict
                  бои ИИ: calculateConflictBattle()
                  бои игрока: открывается ConflictModal
  aftermath     → processAftermath() → раунд + 1 → следующий ход
```

Отложенный приказ хранится в `campaign.pendingOrders` и **не двигает армию** в
момент создания. `moveArmy` только ставит приказ в очередь; снабжение и позиция
обновляются в `executePlayerOrders` по реально пройденному пути (путь может быть
обрезан перехватом).

## 5. Поток данных: бой

### Автобой

```text
scanHotSpots → CampaignConflict
  → previewConflict(...)        силы сторон + defenderModifiers / attackerModifiers / attackerSupply
  → calculateConflictBattle(...)  исход (берёт силы из preview — второй формулы нет)
  → processAftermath(...)
```

`previewConflict` — **единственная** точка интеграции автобоя. Предпросмотр в
интерфейсе и фактический расчёт используют одни и те же числа, поэтому окно
конфликта не может разойтись с результатом.

### RTS-бой

```text
ConflictModal
  ├─ rtsBlockReason            почему бой нельзя запустить (или null)
  ├─ rtsComposition(factionId) составы + бонусы стороны
  ├─ battleConfig              { version, map, slots, colors, handicaps, positions, compositions, … }
  ├─ writeDiagnosticsFile('battles/<ключ>/battle.json')
  └─ prepareAndStartRtsBattle(modId, exe, 'location-cache', entityId, battleConfig)
        │  invoke → Rust
        ▼
     lib.rs: план раскладки BIG → elevated-помощник
        ├─ копирует модули и карты мода в папку игры
        ├─ устанавливает MapCache места боя
        ├─ rts_spawn::generate() → __wotr_generated_presets.big (zzz_spawn.ini)
        ├─ пишет NetworkPref.ini в настоящий профиль
        └─ запускает lotrbfme2ep1.exe
             ▼
     bfme_automation: окно → готовность меню (эталон, 85 %) → «Сеть» → «Лок. сеть»
        → комната (сложность, слоты, цвета, альянсы, точки) → «Начать игру»
        → монитор счёта → match_detector → rts_battle_result_<conflict>.json
             ▼
ConflictModal: readRtsBattleResult(conflictId) → resolveConflictRts(conflictId, winningTeam)
```

От нажатия «BFME» до появления окна игры интерфейс показывает **загрузочный
экран** (`BattleLoadingScreen` + `src/battleLoading.ts`): заставка места боя
(картинка локации или заглушка), локализованное название, текущий шаг и полоса
прогресса.

Состояние — не React и не стор: снимок в модуле с подпиской
`useSyncExternalStore`. Заставка рендерится **только в окне приложения** и
никогда — поверх игры. Это принципиальное ограничение моста, проверенное
экспериментально (0.52.5–0.52.7): клики автоматизации обязаны попадать в окно
игры (`SendInput` бьёт в реальные координаты экрана), поэтому свернуть или
спрятать игру нельзя; перекрывающее окно (даже «сквозное» с
`WS_EX_TRANSPARENT`) ломает мышь в самом BFME, а оконный запуск не даёт
гарантированной геометрии и разрешения после возврата в fullscreen. Итог:
запуск боя — нативный fullscreen (`launch.windowed: false`), игра перекрывает
заставку естественно, и ничто наше над ней не остаётся — мышь в бою работает
как в версии без загрузочного экрана.

Прогресс не теряется и после того, как игру развернуло: `ConflictModal` ведёт
крупные шаги сам (`spawn_generation` → `network_prefs` → `game_launch` →
`ready`); мост на каждой фазе атомарно перезаписывает `temp/rts_progress.json`
(`write_battle_progress`: `spawn_generation` 5 → … → `ready` 100), интерфейс
опрашивает его командой `read_rts_progress` раз в 0.8 с; событие
`battle-loading-progress` из Rust — задел на прямые emit'ы. Технические имена
шагов у всех трёх совпадают с таблицей `BATTLE_LOADING_STEPS`, русские тексты в
ней, английские — в `UI_EN`. Пока заставка видна, шаг и процент дублируются в
**заголовок окна приложения** — он виден в панели задач в любой момент боя.
`ready` (100 %) скрывает заставку сам через ~1.6 с; когда watcher видит исход
боя, заставка возвращается в режиме результата («Обработка результата…», бегущая
полоска) и уходит сама через ~3.2 с, открывая отчёт. Заставка не интерактивна
(`pointer-events: none`).

Все захваты на этапе автоматизации (готовность меню, «room-before-start»)
снимают окно игры через `PrintWindow` с
`PW_CLIENTONLY | PW_RENDERFULLCONTENT` (`capture_window_frame`) — кадр берётся
из поверхности окна, поэтому любые перекрывающие окна в него не попадают.
Монитор результата после старта боя продолжает снимать **экран**: игра тогда
fullscreen и не перекрыта, а PrintWindow для эксклюзивного fullscreen ненадёжен.

Бонусы сторон передаются **одним механизмом**: `rts_spawn.rs` читает
`participant.bonuses` у каждого участника и выдаёт стартовые ресурсы, очки
командования, стартовые очки палантира, доход палантира и сигнальный огонь.
Защитник получает `collectOwnerModifiers(...)` локации, атакующий —
`attackerModifiers` из привезённого снабжения; сигнальный огонь до атакующего
дойти не может, потому что `attackerSupplyModifiers` оставляет только
экономическую часть (`economicPart`) — сигнальный огонь, бонус обороны, засады и
штрафы местности в обоз не грузятся.

## 6. Снабжение (0.51.x)

Обоз везёт **только экономическую часть** бонусов точки отправления: стартовые
ресурсы, очки командования, палантир. Сигнальный огонь, бонус обороны, засады и
штрафы местности не перевозятся.

```text
довезённое = экономическая часть × decayFactor × supplyRatio   (округление вниз)
decayFactor = 1 − гексов × decayPerHex − ходов × decayPerTurn   (в [minRatio, 1])
```

Пул сбрасывается в `null` при достижении `minRatio` (с записью в журнал).
Пополнение на своей локации обнуляет оба счётчика. Вес снабжения в автобое:
`ресурсы/100 × 3 % + КО/50 × 2 % + палСтарт/5 × 2 % + палДоход × 3 %`.

Настройки — `supplySettings` в `world.json`, правятся в редакторе мира.
Отсутствие блока в моде даёт значения по умолчанию (`DEFAULT_SUPPLY_SETTINGS`,
`enabled: true`).

## 7. Инварианты

- **Один объект на гекс.** Гекс объекта — стабильный осевой ID `"q:r"`; пиксельная позиция выводится из центра гекса.
- **Каждый сухопутный гекс принадлежит ровно одному региону.** Гексы владения генерируются автоматически и не пересекают границы региона; оплот вырезается из окружающих владений.
- **Имена не являются идентификаторами.** ID стабильны, имена локализуются.
- **Первый слот RTS не кликается** — его задаёт `NetworkPref.ini`.
- **Стартовые флажки — один клик на слот.** Комната BFME ставит флажок следующему слоту (1, 2, 3, …), поэтому `assign_start_positions` (и эталон `room.py`) кликает каждый слот ровно один раз в его точку, по возрастанию номеров. Владелец крепости может быть любым слотом — первый слот всегда игрок, и он может атаковать, пока крепость обороняет бот.
- **«Крепостной» бой определяется картой места боя** (`rtsFortress.defenderStartPosition` + `rtsPositions.fortressDefenseIndex` у объекта), а не стратегическим типом «осада»: крепостные карты BFME есть и у столиц (Минас Тирит), и у шахт (Эребор). Без точки защитника (Каир Андрос) расстановка идёт как у обычной локации.
- **Диагностика пишет разрешение рабочего стола, а не игрового режима.** Полноэкранный BFME временно переключает режим дисплея, а «сохранённый» режим из реестра Windows на некоторых машинах хранит устаревшую запись (640×480 при рабочем столе 1920×1080). Поэтому разрешение и геометрия дисплеев снимаются в `snapshot_desktop_at_launch()` — при запуске боя, ДО старта BFME, когда текущий режим (`ENUM_CURRENT_SETTINGS`) гарантированно равен рабочему столу; этот снимок используется в `environment.json`/`analysis.json` и в именах PNG (`кадр@экран`), игровой режим виден по `gameWindow` и размеру кадра.
- **Файл исхода боя — один на конфликт и переживает запуски.** `rts_battle_result_<conflict>.json` удаляется при каждом новом запуске боя, а watcher исхода игнорирует записи, сделанные раньше старта попытки: после аварийного выхода по Ctrl в файле остаётся `ABORTED`, и без этой очистки повторный бой не дождался бы настоящего результата.
- **Разрешение игры не меняется.** Детектор масштабирует шаблоны под кадр, а не наоборот.
- **Над игрой не рисуется ничего нашего.** Загрузочный экран боя живёт только
  в окне приложения (`pointer-events: none`, `cursor: none` внутри него);
  перекрывающих окон, topmost-стилей и оконного режима игры нет — иначе ломается
  либо клики автоматизации, либо мышь в самом BFME (проверено в 0.52.5–0.52.7).
  Пока идёт автоматизация, захваты моста идут через `PrintWindow` по HWND окна
  игры — кадр не зависит от того, что перекрывает игру.
- **У каждого контрола есть CSS-правило.** Тема тёмная, браузерные контролы светлые: непокрытая кнопка или поле выглядят белой заплаткой. Галочки и радио получают глобальные `accent-color` и размер 13 px в `global.css`; правила, задающие вид текстовых полей, обязаны исключать `[type='checkbox']` и `[type='radio']`, иначе галочка растягивается в белый квадрат.
- **Каждая русская строка интерфейса имеет запись в `UI_EN`.** Локализатор DOM подставляет английский по точному совпадению строки, поэтому пропущенная запись — это русская надпись в английском интерфейсе.
- **Версия в пяти файлах всегда совпадает**; `check-version` роняет сборку при расхождении.
- **Сохранения не мигрируются.** Новая версия — новая кампания.

## 9. Подводные камни

Список из реальной практики — всё это уже стоило времени:

- **`calculateAutoBattle` не вызывается нигде.** Меняя автобой, правьте `previewConflict`; иначе изменения ни на что не повлияют.
- **`moveArmy` не двигает армию** — только ставит приказ. Состояние меняется в `executePlayerOrders` по фактически пройденному пути.
- **Начало хода стороны — это `preparePlanningSide`**, а не исполнение приказов: доход и пополнение снабжения относятся именно туда.
- **Производные значения в компонентах должны идти после значения, которое читают.** Иначе TypeScript ловит `TS2448: Block-scoped variable used before its declaration`.
- **Один и тот же JSX-фрагмент может встречаться в нескольких редакторах** (`WorldDataEditor.tsx` содержит похожие блоки для экономических типов, построек и регионов). Правка «по первой найденной строке» молча меняет не тот блок.
- **Добавление обязательного поля в тип** вылезает во всех литералах по кодовой базе (`TS2741`) — `npx tsc --noEmit` единственный надёжный способ это собрать.
- **`verify/cases.tsx` проверяет и правила интерфейса, и буквальные строки журнала.** Перед изменением текста журнала — grep по харнессу.
- **ID фракций берутся из данных мира.** В тестовой кампании харнесса это `men-of-the-west`, а не `gondor`; читайте `campaign.playerFactionId`.
- **Rust собирается вслепую там, где нет crates.io.** Не используйте `.into()` на приёме дженерика (`impl AsRef<str>`) — будет E0283; передавайте литерал напрямую.
- **PNG пишется собственным энкодером** (без крейта `png`): поток deflate сохранён без сжатия, размеры кадра зашиты в имя файла.
- **Журнал не резиновый:** `describe()` в `sessionLog.ts` обрезает строки длиннее 120 символов, массивы длиннее 12 элементов и весь результат до 400 символов, поэтому мир целиком в строку журнала не попадает.
- **Блокировка ввода в мосту** держится только на время автоматизации; тяжёлую работу в callback низкоуровневого хука делать нельзя — Windows снимет хук по таймауту.
- **PrintWindow и эксклюзивный fullscreen.** `capture_window_frame` (PrintWindow)
  надёжен для оконного и композитного fullscreen, но для эксклюзивного
  fullscreen DirectX-окно часто печатается чёрным — поэтому он применяется
  только на этапе настройки боя, пока игра оконная, а монитор результата снимает
  экран. Не «объединяйте» эти два пути захвата.
- **UAC нельзя обойти.** Помощник моста требует повышения на каждый запуск боя
  (запись BIG-файлов в папку игры + права на ввод для `game.dat`); запрос
  согласия рисуется Windows на защищённом рабочем столе поверх всего. Отмена
  запроса = отмена боя: `run_elevated_helper` вернёт ошибку, загрузочный экран
  скроется, а окно конфликта покажет причину.
- **Игру нельзя ни спрятать, ни перекрыть на время автоматизации.** `SendInput`
  кликает по реальным координатам экрана — свернутое/спрятанное окно клики не
  получит; перекрывающее окно отбирает клики у игры и ломает её мышь. Все
  попытки (0.52.5–0.52.7: topmost-маска, оконный запуск, Alt+Enter) отменены;
  если захочется вернуть «кинематографичность» — только через ввод без реального
  курсора, которого у SAGE нет.

## 10. Проверка изменений

```powershell
npm run build                    # check-version → tsc → vite
npm install --no-save jsdom      # один раз
node verify/run.mjs              # 68 проверок игровой логики
node verify/i18n.mjs             # покрытие словаря интерфейса
node verify/styles.mjs           # каждый контрол прикрыт CSS-правилом
```

`verify/styles.mjs` рендерит настоящие экраны (все вкладки редактора данных,
игровые панели с выбранной локацией и армией) в jsdom с настоящими таблицами
стилей и сравнивает вычисленные стили каждого контрола с «голым» контролом
вне контейнеров: совпадение значит, что до элемента не дошло ни одно правило и
браузер рисует свой светлый контрол на тёмном интерфейсе. Для чекбоксов и
радио критерии отдельные: незаданный `accent-color` (браузерная светлая
галочка) и размер больше 20 px — признак того, что галочку растянуло правило,
написанное для текстового поля (`width:100%; height:30px`); такой чекбокс
выглядит пустым белым квадратом.

`verify/i18n.mjs` собирает все статические русские строки из `src/components`
и прогоняет их через настоящую `translateText()`: всё, что в английском
интерфейсе остаётся с кириллицей, — пропущенная запись словаря.

Харнесс собирает **настоящие** исходники через esbuild и исполняет их в jsdom:
проверяются стор, журнал сессии, правила кликов по карте и арифметика
снабжения. Он не входит в `npm run build` и не подключён к `tsconfig`.

Rust-часть (`src-tauri/`) собирается только на машине с доступом к crates.io и
Windows SDK; там же есть unit-тесты на таблицу апгрейдов героев. Если сборка
недоступна, правки проверяются чтением диффа — и это стоит проговорить явно, а
не выдавать за проверенное.
